# 10-11-platform-subtitle-cache

## Goal

平台字幕（B站/抖音/YouTube）成功获取并判定正确后注入缓存池；同一视频重新处理/重试时
优先命中缓存，跳过"重新探测 + 内容抽查"，避免因平台侧瞬态失败（风控 412 / 字幕 body
先残后全）而白跑一次全量转录。

## 具体例子

同一个 B站视频处理两次：

- 第一次：字幕探测成功 + 内容抽查通过 → 正常用字幕，**同时写入缓存**。
- 第二次（重新处理/重试）：B站这次 412 或返回残字幕 → 现状会回退到 `_acquire_audio`
  + 全量转录（云端计费或本地数分钟）。**期望**：直接命中上次缓存字幕，秒级跳过，
  既不再探测也不转录。

## Requirements

- 新增 `op='subtitle'` 缓存类型，复用现有 `ai_cache` 表（无 schema 迁移）。
- 键 = 平台标识 + 视频 ID + 语言；**不含音频哈希**（字幕路径本就不下载音频，
  命中时连音频都不用下）。
- 写入时机：字幕确实拿到**且判定正确**——B站/抖音 = 内容抽查 `passed`；
  YouTube（无抽查环节）= 抓取成功。其他状态一律不写。
- 读取时机：位于三个平台字幕分支之前；命中即把 SRT/TXT 写回 `job_dir`、
  meta 标记 `subtitle_check='cached'`、跳过探测与抽查，直接进下游。
- `force_transcribe=true`（用户明确要转录）：不读、不写。
- `bypass_cache=true`（忽略缓存）：跳过读取但成功仍写回（与 ASR 缓存语义一致）。
- `AI_CACHE_ENABLED=0`：整体不介入，行为与改造前逐字节一致。

## 决策（本轮确认，采用推荐默认）

- **命中不重新抽查**：缓存条目当初已抽查通过，直接使用（省掉 90s 音频下载 + Whisper 抽查）。
  代价：视频被换源时可能长期复用旧字幕——由「忽略缓存」开关兜底。
- **抽查异常（unavailable）不写缓存**：与「宁缺勿错」一致，只有确证正确的字幕才落池。
- **不设 TTL**：靠「忽略缓存」开关 + 条数上限淘汰（与 AI/ASR 缓存一致）。

## Acceptance Criteria

- [ ] 同一 B站视频连续两次处理：第二次命中字幕缓存（日志可见「命中平台字幕缓存」），
      `extract_bilibili_subtitles` 零调用、不下载 90s 抽查音频、不发生转录。
- [ ] 抽查未通过（错位）时**不**写缓存。
- [ ] 抽查异常 `unavailable` 时**不**写缓存。
- [ ] YouTube / 抖音字幕成功同样写缓存并可命中。
- [ ] `force_transcribe=true` 时不读也不写字幕缓存。
- [ ] `bypass_cache=true` 时跳过读取、但成功仍写回。
- [ ] `AI_CACHE_ENABLED=0` 时行为与改造前一致（完全不介入）。
- [ ] 回归：`backend/tests/test_url_input.py` 全绿；新增单测覆盖上述边界。

## 不做项

- 不改 B站字幕提取/选轨/抽查/412 退避逻辑（只在其外围加缓存读写）。
- 不改 `ai_cache` 表结构、不改 ASR / AI 缓存语义。
- 不引入 TTL / 独立容量池（沿用现有 `AI_CACHE_MAX_ENTRIES` 全局淘汰）。

## 影响范围

- `backend/services/ai_cache.py`：新增字幕缓存读写单点（三个函数）。
- `backend/main.py::_handle_url_input`：加命中/写入点（三个平台分支）。

## 风险与回滚

- 风险等级：**M1**（跨模块但方案清晰，无 public API / schema / 安全边界变化）。
- 不可逆操作：无（纯新增缓存条目；`AI_CACHE_ENABLED=0` 或删表即回滚）。
- 回滚方式：`git revert` 本轮 commit；缓存条目是加速项，残留不影响正确性。
- 已知风险：视频换源后可能复用旧字幕（本轮已确认接受）。
