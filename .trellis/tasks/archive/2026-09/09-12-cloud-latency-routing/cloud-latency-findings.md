# 云端为何突然变慢：诊断数据 + 路由递归方案总结

> 2026-09-12 | 起因：BV1bH4y1r75q 对比中云端 10 分钟音频耗时 848s（0.71x 实时），
> 用户质疑"不是有提速策略"。本文为实测诊断结论与落地的路由改进。

## 一、根因：服务端排队抖动，不是本地并发不足

实测（同一段 120s 音频切 18 片，每片 ~6.7s，串行/并发对照）：

| 实验 | 数据 | 结论 |
|---|---|---|
| 单片延迟（4 并发） | 7s 片：6.4s ~ 138.5s；28s 片：304s（180s 超时+重试） | **延迟与分片大小强相关**，且同规格波动 20 倍+ |
| 并发 8 vs 16（同 18 片） | c8：总 230.5s（med 108s / max 230s）；c16：总 **360.3s**（med 35s / max 360s） | **提高并发反而更慢**：中位更快但长尾更长（服务端账号级排队惩罚） |

要点：
1. SiliconFlow SenseVoice 是排队式推理，单片延迟 1s~360s 随机波动，服务端状态决定一切。
2. "提速策略"（并发 16、分片 3~30s）在延迟抖动面前无效——总耗时 ≈ 最慢单片 + 重试罚时。
3. 28s 大片会撞 180s 超时然后重试，单片罚时 300s+；小片（~7s）才有 6.4s 的快路径。
4. 结论：云端参数没有可挖的提速空间，**正确的"提速"是不走云端**（本地 FireRedASR 3.6x 实时且更准）。

## 二、落地改进（commit 24df917 之后的递归路由 commit）

### 2.1 引擎级递归回退链（transcriber.py 单点路由重写）

```
cloud → firered(模型就绪时) → local(Whisper)
firered → local
local →（无回退，链尾失败上抛）
```

- 递归实现：`_FALLBACK_CHAINS` 静态链 + 循环降级，每级失败原因经 progress_callback 可见
- **firered 只在模型就绪时参与回退**——兜底绝不触发 1.1GB 下载（下载只发生在用户显式选 firered）
- 取消在任何一环直接上抛，不回退；链尾（Whisper）失败无路可退直接抛
- 旧语义保持：`local`=Whisper 不变，非法引擎值按 cloud 链

### 2.2 分片级递归补救（cloud_asr.py，"单片失败留空洞"正式关闭）

云端单片失败不再跳过留洞，当场换本地引擎补录该分片：

```
失败片 → firered（模型就绪，transcribe_chunk_text）
       → Whisper base（固定 CPU，中文带简体提示词，与字幕抽查同路径）
       → 都失败才留空（日志可见）
```

- 补录发生在 finally 清理分片文件**之前**；补录文本按原时间轴并入结果，句级化逻辑复用
- 全部分片失败但补录有收获 → 不再抛 Unavailable（此前会整体回退丢掉全部云端结果）
- 进度/完成文案透出补录信息：`N 片由本地引擎（FireRedASR）补录`

### 2.3 延迟画像日志（诊断"云端突然变慢"的眼睛）

每次云端转录结束记录：`云端分片延迟画像: n=88 min=1.2s 中位=35s p90=210s max=300s（并发 8，总耗时 848s）`。
中位数高=服务端排队严重；p90/max 高=长尾片拖累——下次再问"云端怎么慢了"，看一行日志即可定位。

## 三、经验教训

1. **外部服务的延迟抖动不是并发数能治的**——先测延迟分布（min/med/p90/max），再谈调参。
2. **提高并发放大了长尾**：c16 med 更快（35s vs 108s）但 max 更糟，总耗时反升 56%。排队式服务要控并发而非堆并发。
3. **自建本地引擎后，回退链应该是"递归"的**：每级失败都把子问题交给下一级（引擎级→分片级），而不是非黑即白地整体回退。
4. **兜底路径不能有重副作用**：firered 作为兜底参与回退时绝不触发模型下载。
5. 测试隔离：注入分片失败的编排测试必须显式禁用补录路径，否则测试机会真实加载 1.3GB 模型（本机实测 24s）。
