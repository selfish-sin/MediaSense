# BV1bH4y1r75q 云端 vs 本地 FireRedASR 对比报告

> 2026-09-12 | 应用户要求砍量：取视频**前 10 分钟**（原 62 分钟全量跑云端耗时过长）
> 音频：《经络辨证和针灸处方》（中医针灸课，清晰中文讲课，含少量口语碎片）
> 原始产物：`compare/` 目录（双引擎 SRT/TXT + timing.json）

## 一、速度（同一 10 分钟音频，串行实测）

| 引擎 | 耗时 | 实时倍率 | 说明 |
|---|---|---|---|
| 云端 SenseVoice | **848.4s（14.1 分钟）** | **0.71x（慢于实时）** | 88 分片 × 8 并发，排队式推理延迟 ~90-180s/片是瓶颈 |
| 本地 FireRedASR2-AED | **168.8s（2.8 分钟）** | **3.6x 实时** | 3 线程 + 6 路段间并行解码（本次实测落地的提速项） |

**本地反比云端快 5 倍**。云端瓶颈在服务端排队延迟，分片并发已到 8（账号级 RPM 上限内），
再提并发空间有限；本地提速项见 §三。

## 二、质量（同段音频逐窗口并排核对）

| 指标 | 云端 SenseVoice | 本地 FireRedASR2 |
|---|---|---|
| SRT 条数 | 140 | 120 |
| 总字数（去标点） | 2074 | **2174（多 100 字）** |
| 假名幻觉（ hallucination 特征） | **8 处**（「あ问なま」「そか」） | **0 处** |
| 最大单条时长 | 9.3s | 11.6s |

典型差异（原文见 compare/ 下 SRT）：

1. **开头碎片段**：云端把不清晰语音幻觉成日文（「あ问なま。」「大数据。そか。」）；
   本地只输出「好嗯，这个先不用看那个。」——碎片噪音不硬编。
2. **中段丢字**：云端「数在里上，这个就是你整个看病的过程」丢了主语半句；
   本地「往里的操作它是有数在里的，这个就是你整个看病的过程是这样的」完整。
3. **术语与形近字**：结尾针灸术语「内关加外关」，本地「内关加外冲」接近；
   云端「内框架再冲」完全走样；「他可能本身就心慌了」本地正确，云端「可定」错。
4. **标点**：两者均为句级标点（本地走外接标点模型，云端 API 自带），体验一致。

**结论**：该中文场景下本地 FireRedASR2 文本质量优于云端 SenseVoice
（丢字更少、无幻觉、术语更准），且速度快 5 倍、无 API 成本、离线可用。

## 三、本地引擎提速落地（本报告实测产出）

60 秒样本扫参（文本逐字一致，纯速度差异）：

| 配置 | RTF | 结论 |
|---|---|---|
| threads=3 串行（原实现） | 0.402 | 基线 |
| threads=8/16 串行 | 0.471/0.823 | ❌ 线程多了反而互相踩 |
| **threads=3 + 6 路段间并行** | **0.214** | ✅ **1.9x，已落为默认** |

- 实现位置：`local_asr.py` 识别主循环改 `ThreadPoolExecutor` 段间并行
  （onnxruntime Run 释放 GIL，真并行）；标点恢复仍主线程串行（0.01s/段可忽略，
  且不假设其并发安全）。
- 参数可调：`FIRERED_NUM_THREADS`（默认 3）/ `FIRERED_DECODE_WORKERS`（默认 6）。
- 另两条路（未走）：FireRedASR2-**CTC** 版 RTF 0.058（再快 3.7x）但错字明显升档
  （官方样例「上好/志高/吃火」三处错），违背"本地最准"定位，不做默认；
  onnxruntime-gpu 可再提速但依赖 CUDA 环境，与 CPU-only 打包策略冲突，暂不做。

## 四、结论与建议

1. 本地 FireRedASR 引擎达到预期：**质量超云端、速度 3.6x 实时、零成本离线**。
2. 云端引擎保留价值：非中英语种、极端长音频不想占本机 CPU 时仍有意义。
3. 62 分钟全量音频按此 RTF 推算本地约 **17 分钟**可完成（云端同源全量预估 >40 分钟）。
